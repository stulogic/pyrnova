# M22-A — Material Changes read model + vertical slice

_Status: implemented 2026-09-09 (M22-A) · additive · governed by
`docs/strategy/PHASE_1_PRODUCT_AUTHORITY.md`, D-041, D-046, D-055_

The first customer-facing productization slice: existing Pyrnova intelligence → customer relevance →
Material Change read projection → read API → Material Changes frontend view. It makes Pyrnova begin
behaving like a product without building a parallel intelligence system, altering `scoring_v1`/`fit.py`/
`replay.py`/severity bands, or touching any frozen corpus.

## Customer question

**"What materially changed since I last looked, and why does it matter to this organization?"**

## Components

| Layer | File | Responsibility |
|---|---|---|
| Read model | `pyrnova/material_changes.py` | `CustomerContext`, deterministic `assess_relevance`, `build_material_changes` projection over existing streams |
| Customer context | `examples/material_changes_demo/{torch,dap}.json` | compact, extensible per-customer intelligence context (entity refs, watchlist, agencies, capabilities) |
| Demo seed | `examples/material_changes_demo/build_seed.py` | generates the tracked, replay-safe state fixture from **real archived evidence** (no fabrication, no live calls) |
| Service | `pyrnova/ops.py` (`OperatorConsole.material_changes`, `.customers`) | reads `threats`/`propagated_threats`/`opportunities`, returns the customer feed |
| API | `pyrnova/ops_server.py` (`/api/material-changes`, `/api/customers`) | read endpoints; customer + `as_of` + `disposition` params |
| Frontend | `pyrnova/ops_web/material.{html,css,js}` | customer-facing Material Changes view served at `/` (Operator Console moves to `/console`) |

## Read projection (per material change)

Each Material Change keeps **OBSERVED fact** and **PYRNOVA ASSESSMENT** in separate structured blocks —
never flattened (D-055):

- **observed**: event type, affected entity/ref, affected program, agency, event time, knowable-at
  (point-in-time), origin (OBSERVED vs MODELED catalyst).
- **assessment**: disposition (THREAT / OPPORTUNITY / MONITORING), mechanism, consequence, materiality
  (severity ordinal) and confidence (evidence-strength ordinal) as **orthogonal** values, affected value
  category, `is_assessment: true`, engine version.
- **relevance**: inspectable basis + detail + all matched reasons.
- **evidence**: ids and distinct-authoritative-source count (not evidence bodies); `single_source` flag;
  `raw_authoritative_bytes` flag; catalyst class. Independence is reported conservatively — multiple rows
  from one source are **not** independent corroboration.
- **uncertainty**, **lifecycle_state**, **outcome_state**, **propagation** (path/depth/join class), and
  **refs/provenance** (stable ids back to entity/program/evidence).

## Relevance logic (deterministic only)

`assess_relevance` requires a structured match — never text similarity — and returns an inspectable
basis, strongest first: `DIRECT_SUBJECT` (customer is the affected entity), `WATCHED_ENTITY`,
`WATCHED_PROGRAM`, `CAPABILITY_MATCH`, `AGENCY_INTEREST` (monitoring-grade). No LLM relevance agent.

## Invariants (tested — `tests/test_material_changes.py`)

- **Customer isolation**: a change not relevant to a customer is not returned; the two demo customers'
  change sets are disjoint.
- **Observed ≠ assessed**: separate blocks; severity does not live in the observed block; materiality and
  confidence are distinct fields.
- **Point-in-time truth**: a change is visible only when knowable (`observed_at <= as_of`); an
  event-caused threat is not knowable before its triggering event even if a supporting relationship was
  knowable earlier.
- **Evidence referenced, not duplicated**; independence reported conservatively (single authoritative
  source ⇒ `single_source`).
- **Stable ordering**: relevance strength → materiality → confidence → recency → id.

## Demonstration data (real, replay-first)

- **Torch Technologies** — real archived USAspending deobligation on SAIC PIID `47QFSA20F0057` (M19) →
  HIGH-confidence PROGRAM_CONTRACTION for SAIC → one-hop propagation to Torch over the real
  program-anchored SAIC→Torch sub-award edge.
- **DAP Construction Management LLC** — real raw-archived USAspending terminate-for-convenience (M21,
  PIID `36C25726N0240`) → HIGH-confidence PROGRAM_CANCELLATION_OR_DELAY → propagation to the parent over
  the deterministic `SUBSIDIARY_OF` native-id edge; later outcome honestly UNRESOLVED.

The fixture is generated by `build_seed.py` from `examples/real_evidence/` and committed for a populated
fresh-checkout demo. `python -m pyrnova.ops_server` serves the demo fixture when no persisted `threats`
stream exists.

## Documented follow-ups (roadmapped, not swallowed here)

- Evidence-independence lineage: today independence = distinct authoritative source count. A first-class
  evidence-lineage/origin model (multiple genuinely independent confirmations) is an M22 follow-up.
- Opportunity/MONITORING dispositions are supported by the read model but the demo shows only truthful
  THREAT items (no real customer opportunity fixture yet) — grow with real opportunity/consequence data.
- Persisted (non-demo) Material Changes: wire the live engine's `threats`/`propagated_threats` streams
  into `mc_store` once continuous operations persist them.
- Customer boundary hardening: the read path already filters per customer; a real tenancy/authz boundary
  is a later M22 slice (do not assume all customers may see all changes).
